# 催事情報の精査と公開条件

新規・修正情報は「収集 → 原文との再照合 → 自動検査 → 公開」の順に処理する。収集した文章を読み返すだけで確認済みにしない。精査では元ページ・PDF・画像をもう一度開き、掲載予定の各項目と照らし合わせる。検索要約、URLの年、毎年の慣例だけで確定しない。

## 原文との再照合

1. **大会の同一性**：正式名称、回次、開催年、全国決勝／地区予選、主催者を確認する。年度と暦年、案内の掲載日と開催日を区別する。
2. **日時**：開催年・月日と、資料に曜日がある場合は曜日も照合する。開場・開演・終演、申込締切を取り違えない。和暦は西暦に換算して再確認する。資料にない時刻は `null` のまま。
3. **場所**：都道府県、市区町村、施設名、ホール名、住所が同じ会場を指すか確認する。可能なら会場公式の予定表・アクセスページとも照合する。Googleマップの検索語が別の同名施設を指さないか確認する。会場の愛称・改称は開催当時の資料も確認する。
4. **料金**：観覧料の明記があるか確認する。出場料、審査料、教材代、参加者の弁当代から推定しない。無料と書かれていなければ無料扱いにしない。前売／当日・席種・年齢・事前申込の条件を落とさない。
5. **一般見学**：会員向けの出場募集だけでは一般入場可能と判断しない。観覧券・一般向け入場案内、主催者の明記、または日付付きのユーザー判断を根拠にする。料金と一般入場の可否は別々に確認する。
6. **最新告知**：主催者・会場の告知で、中止・延期・会場変更・満席・受付終了・訂正版がないか調べる。古いチラシより訂正告知を優先する。「変更なし」も、実際に確認した範囲を記録する。

主催者公式を優先し、会場・自治体など独立した資料があれば突き合わせる。別サイトの同じチラシ転載は独立した裏付けに数えない。公式資料が一つしかない場合は、一資料であることと確認できた範囲を記録する。X・Facebookは発信者の公式性と投稿年を確認し、画像内の文字も読む。二つ目の根拠や閲覧できなかった内容を作らない。

## 不明・矛盾の扱い

- 開催日・開催地・会場に解消できない矛盾がある新規情報は公開せず、調査ログの確認待ちへ置く。資料を読めないことは、誤り・中止・変更なしの証拠にはしない。
- 料金や一般見学の根拠がない場合は `unknown` とし、料金は `null`。不明点を確定値へ埋めるために推測しない。
- 既存情報の誤りが公式資料で確定したら、同じIDに修正する。未解決の矛盾、中止・延期、表示仕様では正しく案内できない変更を見つけたら、その催事の自動更新を止め、ユーザーへ根拠と影響を知らせる。通常の開催予定として確認日だけを更新しない。保存済み記録は削除しない。
- 確認待ちの催事があっても、別の確認済み催事は公開できる。確認待ちを混ぜたまま検査を迂回しない。

## 精査記録

公開データを確定した後、`python -X utf8 scripts/events/check-reviews.py --prepare E001` のようにIDを指定して未承認のひな型を出す。読み取った根拠を記入し、`scripts/events/reviews.json` の `events` にID別で保存する。ひな型のままでは公開検査に通らない。

- `record_sha256`：精査した催事データ全体の識別値。精査後にデータを編集したら再照合する。
- `reviewed_at`：原文を精査した日。催事の `checked_at` と一致させる。
- `decision`：精査完了時だけ `verified`。確認待ちの `pending` や矛盾の `conflict` は公開不可。未解決の記録はリポジトリ外の調査ログに残す。
- `checks`：上記6項目を `identity`、`schedule`、`location`、`admission`、`audience`、`latest_notice` へ記録する。各項目に `result`、実際に読んだ `urls`、具体的な確認内容を自分の言葉で要約した `note` を残す。URLは掲載データの `sources` にも含める。長文転載や個人連絡先は記録しない。
- `result`：裏付けた項目は `verified`。料金と一般見学が掲載データでも未確認の場合のみ `unknown` とし、読んだ資料に明記がなかった理由を残す。時刻の一部が不明な場合は `schedule.note` に明記し、掲載値を `null` にする。
- `cross_check`：別資料との照合結果、または公式資料が一つしかなく照合できなかった範囲。形式だけの「確認済み」は使わない。

確認記録は公開リポジトリに入る。公開してよい根拠と要約だけを含め、調査の詳しい作業ログ・確認待ちは `../output/research/shigin-events-weekly/YYYY-MM-DD/` に置く。

## 自動で公開を止める検査

更新前のコミットを控え、`python -X utf8 scripts/events/check-reviews.py --base <更新前SHA>` を実行する。未コミットの更新を検査するときは `--base HEAD` でよい。

- 追加・変更に精査記録がない、精査後に内容を変えた、確認URLや項目別の根拠が欠けている、確認結果と掲載値が合わない場合は失敗する。
- 日付・時刻の不整合、同じ催事の重複、未来の確認日、保存済み記録の削除、個別確認なしの全体確認日更新も失敗する。
- GitHub Actionsでも **push前のコミット** と比較し、精査記録・データ・表示・生成結果の一致を検査する。失敗したらCloudflareへ進まず、公開中のページを維持する。
- 自動検査は入力と確認記録の整合性を調べる。外部資料の内容の真偽や読み間違いまで機械で保証するものではない。その部分を原文の再照合と別資料の確認で補う。

## 既存情報の再点検

導入時の90件に、精査したふりの確認記録を付けない。既存情報は変更がなければ公開を維持し、次回から「60日以内の予定 → その他の予定 → 過去」の順で新手順による再点検を進める。予定の再点検は過去情報の新規補完より優先する。進捗は `BACKLOG.md` に記録する。毎回、今回確認した件数・訂正・未解決事項を調査ログへ残し、未確認分まで点検済みと言わない。
